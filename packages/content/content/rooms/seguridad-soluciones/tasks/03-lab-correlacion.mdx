## De eventos a incidente

Un SIEM vale por su **correlación**: cada fuente sola cuenta una historia
aburrida; cruzadas delatan la campaña. El lab expone tres fuentes de la
noche del 31-Oct con un ataque completo:

```bash
curl -s http://127.0.0.1:18107/logs/firewall
curl -s http://127.0.0.1:18107/logs/auth
curl -s http://127.0.0.1:18107/logs/web
```

## El método (pivoting)

1. **Encuentra el común**: ¿qué IP aparece en las tres fuentes?
   ```bash
   # extrae IPs y cruza:
   curl -s http://127.0.0.1:18107/logs/firewall | grep -oE '[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+' | sort -u
   ```
2. **Ordena por tiempo**: recon (scan de /robots, /.env...) → brute force
   SSH → exploit → persistencia → callbacks salientes a `185.221.9.7`.
3. **Valida**: envía tu reconstrucción al motor:
   ```bash
   curl -s "http://127.0.0.1:18107/correlate?ip=<IP>&time=<HH:MM:SS>&persistence=<mecanismo>"
   ```

## Qué cuenta cada fuente

| Fuente | Aporta |
|---|---|
| Firewall | Qué conexiones pasaron (y el scan que rebotó) |
| Auth | Brute force, sesión aceptada, sudo, cron, useradd |
| Web | El path exacto del exploit (command injection) |

Fíjate en el detalle fino: la sesión SSH `Accepted password for deploy`
coincide **al segundo** con la conexión ACCEPT del firewall y con la query
inyectada del access log. Ese anclaje temporal en tres fuentes es la
definición operativa de correlación — y lo que un analista tier-2 hace
todo el día en Splunk/Elastic con reglas mucho más cómodas que grep.
