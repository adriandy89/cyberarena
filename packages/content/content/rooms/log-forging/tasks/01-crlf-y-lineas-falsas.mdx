## Una línea de log = una mentira potential

La app registra tu feedback así:

```python
log_line = f'[INFO] User alice said: {msg}'   # ← msg sin sanear
```

Si `msg` contiene un salto de línea, controlas el inicio de la línea
siguiente. El navegador y curl envían `%0d%0a` (CR+LF) y el servidor lo
graba tal cual:

```bash
curl 'http://127.0.0.1:18102/feedback?msg=hola%0d%0a[SUCCESS]%20Admin%20logged%20in'
```

El log ahora contiene:

```
[INFO] User alice said: hola
[SUCCESS] Admin logged in            ← línea falsa, inyectada por ti
```

## ¿Por qué importa?

- **Forense envenenado**: tras un incidente real, el analista reconstruye
  la línea temporal desde los logs. Líneas falsas = culpables falsos y
  pistas desviadas.
- **Evasión**: ruidos de "éxito" tapan la operación real del atacante.
- **Parsers rotos**: los SIEM que indexan línea a línea indexan tu
  contenido como eventos propios.

Envíalo y reclama la flag, luego mira el resultado:

```bash
curl -s http://127.0.0.1:18102/logs
```

## El fix (una línea)

```python
msg = msg.replace('\r', '').replace('\n', '')   # o mejor: escape de \r\n
```

Los frameworks serios ya lo hacen: structlog y log4j (configurado con
`%replace`) ofrecen conversores que neutralizan saltos de línea. El bug
aparece cuando alguien concatena input directo con `print()` o
`f-string` al logger.
