## El APK por dentro

```bash
unzip -l target.apk
# classes.dex      ← el código (bytecode Dalvik/ART)
# AndroidManifest.xml (binario)
# res/, assets/, lib/ (nativas .so), META-INF/ (firmas)
```

## La pareja estática: apktool + jadx

```bash
# apktool: recursos + manifest legibles + smali
apktool d target.apk -o target-unpacked
cat target-unpacked/AndroidManifest.xml | head -40

# jadx: lógica en Java legible
jadx target.apk -d target-jadx
grep -rn "http://" target-jadx/sources/ | head    # ¿HTTP plano?
grep -rni "api_key\|secret\|token" target-jadx/sources/ | head
```

## El checklist estático del manifest

Lo primero que se lee en cualquier auditoría:

| Indicador | Riesgo |
|---|---|
| `android:exported="true"` sin permiso | Otra app maliciosa puede lanzarlo |
| `android:allowBackup="true"` | Los datos salen por adb backup |
| `debuggable="true"` en release | Depuración attachable = memoria legible |
| Permisos `READ_SMS`/`ACCESSIBILITY` sin justificar | Overpermission |
| `usesCleartextTraffic="true"` | HTTP plano permitido |

Después, el código: credenciales hardcodeadas (strings y grep), URLs
de API internas (que revelan infra), flags de debugging, y el
almacenamiento (`getSharedPreferences`/SQLite en claro vs
EncryptedSharedPreferences).

## OWASP MASVS y MASTG

El marco de referencia móvil (equivalente al ASVS web): **MASVS**
define los requisitos (almacenamiento, cripto, autenticación, red,
resiliencia...) y **MASTG** la metodología de pruebas con recetas por
plataforma. Los hallazgos de arriba mapean directo a MASVS-STORAGE y
MASVS-NETWORK.

La task siguiente rompe la barrera más común cuando el estático no
basta: la app que solo se entiende viéndola correr — y que protege su
tráfico con TLS pinning.
